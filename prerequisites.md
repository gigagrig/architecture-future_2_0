## Инфраструктура для задания 1

Для реального `terraform apply` необходимо подготовить:

1. Аккаунт или сервисную учётную запись у выбранного провайдера и проект/каталог/подписку, где будут создаваться ресурсы.
2. Оплату или учебный грант, если ресурсы платные, и достаточные квоты на ВМ, CPU, RAM, диски и IP-адреса для выбранных конфигураций.
3. Регион и зону размещения, образ ОС, типы дисков и параметры каждой среды.
4. Сеть и Subnet ID для каждой среды либо права на создание сети и подсетей отдельной конфигурацией. Подсеть должна существовать к моменту создания ВМ, если модуль получает её ID на входе.
5. Права на чтение, создание, изменение и удаление управляемых ВМ, дисков и сетевых ресурсов. Конкретные роли определяются после выбора провайдера и состава Terraform-ресурсов.
6. Публичный SSH-ключ для конфигурации ВМ. Для проверки входа также нужны соответствующий приватный ключ, имя пользователя и сетевой маршрут до ВМ; публичный IP требуется только при выбранном способе подключения.

Среды dev, stage и prod в учебном проекте означают разные конфигурации. Доступ к реальной промышленной инфраструктуре компании не нужен. Размеры ВМ условием не заданы; их следует выбрать в пределах доступных квот и бюджета. После проверки нужно удалить временные вычислительные ресурсы и диски, которые больше не используются.

### Пример при выборе Yandex Cloud

Потребуются идентификаторы облака и каталога, зона, Subnet ID и доступ сервисного аккаунта к ресурсам каталога. Один из вариантов аутентификации Terraform — авторизованный ключ сервисного аккаунта. Конкретный способ следует выбрать при реализации по [документации аутентификации провайдера](https://yandex.cloud/en/docs/terraform/authentication).

В текущем MVP используется Yandex Cloud. Пример настройки приведён в [README модуля ВМ](./Task1Advanced/README.md).

## Удалённое состояние и CI/CD для задания 2

Используются Yandex Object Storage, YDB Serverless с Document API для блокировки state и GitHub Actions. [README CI/CD](./Task2Advanced/README.md) содержит bootstrap dev-backend, настройки GitHub Environments и инструкции запуска. Исполняемые workflow находятся в `.github/workflows`. Terraform в этом корне фиксирован на 1.11.4 из-за выбранного механизма блокировки.

### S3-совместимое хранилище

Нужен один из вариантов, указанных в условии: AWS S3, Yandex Object Storage или MinIO. Подготовить следует:

- Существующий bucket, регион и endpoint, если он требуется выбранному сервису. Bucket должен быть доступен до инициализации основного Terraform backend; его создание требует отдельного первоначального шага.
- Отдельный путь к state для каждой среды, чтобы dev, stage и prod не перезаписывали состояние друг друга.
- Учётные данные для S3 API: access key ID и secret access key либо поддерживаемый сервисом способ получения временных учётных данных. Доступ к API создания ВМ и доступ к S3 backend настраиваются отдельно, даже если используется один сервисный аккаунт.
- Права чтения и записи объектов состояния и необходимые права просмотра bucket. Для блокировки состояния нужны дополнительные права, соответствующие выбранному механизму.
- Сетевую доступность хранилища с рабочей машины и из CI/CD. Для MinIO нужно устойчивое хранилище данных; адрес `localhost` рабочей машины не будет доступен облачному runner.

При реализации нужно проверить совместимость выбранного S3-сервиса с backend и механизмом блокировки, чтобы исключить одновременную запись state. HashiCorp тестирует S3 backend с Amazon S3; совместимость альтернативных реализаций нужно проверять отдельно. Параметры доступа и блокировки описаны в [документации S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3).

### CI/CD

- Выбрать одну платформу: GitHub Actions, GitLab CI/CD, Jenkins или другую систему по условию.
- Обеспечить доступный runner/agent с Terraform, Git и сетевым доступом к API провайдера, хранилищу состояния и источникам провайдеров.
- Получить права на настройку pipeline, переменных/секретов и ручного запуска или подтверждения `apply`.
- Передать в CI/CD доступ к API инфраструктуры и S3 backend через хранилище секретов платформы или поддерживаемую федерацию удостоверений. Приватный SSH-ключ ВМ нужен в CI только если pipeline действительно подключается к ВМ.
- Предусмотреть запуск `init`, `plan`, затем подтверждённого `apply` для выбранной среды и исключить конкурирующие изменения её state.

Доступ к Git-платформе нужен для публикации и работы pipeline. Отдельный токен её API требуется только при выборе автоматизации, которая вызывает этот API; само условие такой интеграции не требует.

## Материалы для заданий 3–5

Для архитектурных документов достаточно исходного условия и [схемы текущих потоков данных](./sprint-11-data-flows.png). Нужен инструмент, позволяющий сохранить схемы в репозиторий: например, draw.io, Mermaid или PlantUML. Выбор инструмента определит зависимости для экспорта. Платная подписка на сервис диаграмм не является требованием задания.

Для TCO на три года необходимо собрать или явно задать как допущения:

- Объёмы хранения, прирост данных, вычислительную нагрузку и сетевой трафик.
- Требуемые среды, резервирование, резервные копии и географию размещения.
- Цены инфраструктуры и лицензий с датой, валютой и ссылкой на источник.
- Трудозатраты и стоимость сопровождения, миграции, обучения и времени аналитиков.
- Оценки затрат текущей архитектуры для сравнения с целевой.

В условии нет полного набора числовых данных для TCO. Его можно подготовить на основе публичных тарифов и обозначенных допущений; доступ к реальной бухгалтерии компании не требуется.

Доступы к медицинским, банковским и ИИ API, реальные данные пациентов, лицензии SQL Server/Power BI/PowerBuilder и развёртывание всей целевой платформы для заданий 3–5 условием не требуются. Эти системы описываются в архитектуре; интеграционный прототип с ними не задан.
