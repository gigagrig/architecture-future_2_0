# Архитектура платформы данных

Целевая архитектура на 36 месяцев от старта трансформации: доменные продукты данных, портал самообслуживания и событийные интеграции.

## Назначение и ограничения

Платформа даёт сотрудникам каталог данных, готовые отчёты и конструктор собственных срезов в пределах доступа. Домены самостоятельно развивают продукты данных; подключение нового направления не требует добавлять бизнес-логику в общий DWH. Продукт данных — принадлежащий доменной команде набор аналитических таблиц и представлений с контрактом, владельцем, правилами качества и поддержки. Его выпуск имеет идентификатор release и фиксированный состав таблиц; версия контракта и версия выпуска различаются.

Медицинские карты, истории болезней и результаты исследований не попадают в аналитические события, витрины, архивы или отчёты. Даже ссылка на результат ИИ не передаётся в общий аналитический контур. Для управления клиниками допускаются отдельно согласованные агрегированные показатели загрузки и финансов, а не выгрузка клинических записей. По умолчанию новое поле закрыто для публикации.

## Домены и ответственность

| Система/домен | Источник истины на целевом горизонте | Аналитический продукт | Владелец |
| --- | --- | --- | --- |
| Работа с пациентами | Клиническое приложение и закрытое клиническое хранилище | Агрегированная загрузка клиник без карт и диагнозов | Медицинский директор |
| Медицинский ИИ | Сервис исследований, закрытое хранилище результатов | Техническая загрузка и стоимость обработки без результатов | Руководитель ИИ |
| Банковские продукты | Банковская система договоров и проводок | Кредитный портфель, обезличенная экономика продуктов | Владелец финтеха |
| Расчёты клиник | Сервис счетов и оплат | Выручка, задолженность, сверка платежей | Финансовый директор |
| Персонал и активы | Корпоративные сервисы/ERP | Агрегированные ресурсы и инвентарь | Операционный директор |
| Фарма и оборудование | Собственные контексты поставок и устройств | Поставки, остатки, техническая доступность устройств | Владельцы новых направлений |

Один клиент в банке и пациент в клинике не получают общий публичный идентификатор в аналитике. Междоменные KPI связываются по бизнес-измерениям (период, организация, продукт), а не по медицинским записям. Продукт «Показатели группы» принадлежит финансовой аналитической команде головного офиса: она определяет формулы, периоды и исключение двойного учёта. Суммы кредитования и оплаты клиник не складываются в общую выручку автоматически.

## Контейнеры и компоненты

Go — основной язык новых API-сервисов, включая API портала. Проверка доступа, планирование запросов и фоновые задания отчётов реализуются как компоненты этого Go-приложения. Java / Kafka Streams используется отдельно для потоковых обработчиков продуктов данных. Существующие доменные сервисы сохраняют свой стек на период миграции.

[C4 L2](diagrams/c4-containers.svg) показывает платформу как одну программную систему, а доменные приложения как её поставщиков. Базовая аналитическая платформа — lakehouse, то есть таблицы поверх объектного хранилища:

| Контейнер / формат | Ответственность |
| --- | --- |
| Yandex Object Storage | Разрешённые входные пачки и данные Iceberg; отдельные бакеты/роли по доменам и регионам, изоляция входной и опубликованной зон |
| Apache Iceberg / Parquet | Формат таблиц и файлов с версиями состояния; не отдельный сервис |
| Dremio | SQL-запросы, преобразования и запись Iceberg; базовый технический каталог — встроенный Open Catalog |
| Airflow / Python | Планирование загрузок, SQL-заданий, проверок качества, публикации и обслуживания; вычисления над таблицами выполняет Dremio |
| PostgreSQL для Airflow | Состояние запусков; отдельная служебная схема контрольных точек загрузки с доменными ролями |
| OpenMetadata | Бизнес-каталог: владельцы, контракты, происхождение и качество; не заменяет технический каталог Iceberg |
| Nessie + PostgreSQL, условно | Ветки и согласованная публикация нескольких таблиц; альтернативный технический каталог для выбранных продуктов |
| ClickHouse, условно | Потоковые оперативные витрины, если измеренная задержка lakehouse недостаточна |

В пилоте используются Object Storage, Iceberg, Dremio и Airflow. Nessie включается, если нужен выпуск связанных таблиц через проверяемую ветку. У таблицы один авторитетный технический каталог: Open Catalog или Nessie. Ветки Nessie не являются границами безопасности. ClickHouse не обязателен для базового пути и не получает копию каждого продукта. Редакция Dremio должна поддерживать выбранные каталог и политики доступа; стоимость платных возможностей учитывается при выборе поставки. MinIO Community в промышленный контур не включён.

Домен владеет схемами, SQL-преобразованиями, DAG (графами задач Airflow) и правилами качества своего продукта. Платформа предоставляет шаблоны, сервисы и эксплуатацию. Код разных доменов выполняется в изолированных рабочих средах с отдельными секретами и квотами; UI-роли Airflow сами по себе не обеспечивают изоляцию исполняемого Python. Операционные БД не доступны порталу. Медицинский контур изолирован от аналитического, включая брокеры, хранилища и ключи.

[C4 L3 API портала](diagrams/c4-components.svg) раскрывает проверку прав и выполнение отчётов. Планировщик использует зарегистрированную семантическую модель и фиксирует разрешённый release продукта из PostgreSQL. Dremio Query Adapter отправляет SQL-задание по HTTPS, проверяет статус и получает результат. Используется роль чтения конкретного домена; план содержит разрешённые строки и столбцы. Fast Mart Adapter задействуется только для продуктов ClickHouse. Произвольный SQL пользователя не исполняется, доступ пользователей к бакетам, staging и техническим каталогам закрыт.

Сервис заданий хранит определения отчётов и очередь в PostgreSQL. Worker проверяет актуальные права перед выполнением, а выдача результата — перед скачиванием. Зафиксированный release не отменяет отзыва прав. Результаты небольших отчётов временно хранятся в метаданных; крупные экспорты в эту модель не входят.

[C4 L3 Airflow](diagrams/c4-pipeline-components.svg) раскрывает выпуск продукта: загрузка разрешённых данных → построение версии-кандидата через Dremio SQL → проверки → публикация. Отдельный DAG обслуживает файлы и сроки хранения. Airflow управляет конечными пакетными заданиями и пересчётами; непрерывное чтение Kafka выполняют доменные обработчики.

При недоступности проверки прав выдача данных прекращается. Аудит хранит субъект, продукт, решение, время, объём и correlation ID без содержимого медицинских данных. Журнал аудита — отдельная PostgreSQL-база. Audit Writer записывает решение по SQL/TLS и ожидает подтверждения транзакции до выдачи данных. Роль приложения имеет только INSERT; чтение и обслуживание журнала выделены отдельным ролям. Если запись не подтверждена, критичное действие блокируется. Метрики и трассы идут отдельно через OpenTelemetry Collector и могут буферизоваться; их приём не подтверждает запись аудита.

## Путь данных

1. Доменные приложения фиксируют изменение бизнес-сущности и запись outbox в одной локальной транзакции. Outbox — журнал ожидающих публикации событий; отдельный процесс повторяет доставку до подтверждения брокера.
2. Закрытые операционные события доступны только разрешённым доменам. Отдельный доменный проектор строит разрешённые аналитические факты/агрегаты. Он не копирует всё содержимое события в общий Kafka.
3. Обработчик продукта проверяет контракт и записывает разрешённые события пачками в Object Storage через S3-клиент. Объект имеет устойчивый ключ по домену, партиции и диапазону offsets; подтверждение чтения Kafka следует после записи. Повтор после сбоя не должен создавать второй эффект. Если выбран ClickHouse, его проекция обновляется независимо и имеет собственную контрольную точку: общей транзакции с S3 нет.
4. Airflow получает перечень завершённых пачек либо запускает разрешённый экспорт через доменный адаптер. Контрольная точка загрузки хранится отдельно от факта запуска DAG. Dremio SQL строит таблицы Iceberg версии-кандидата, устраняет дубликаты по event_id и выбирает последнюю aggregate_version по ключу. Полный аналитический срез заменяет предыдущий, не прибавляется к нему. Legacy-экспорт использует устойчивый ключ/версию и сверку; клинические поля исключаются до передачи в аналитическую зону.
5. Необрабатываемые события поступают в ограниченную dead-letter queue (DLQ), то есть очередь ошибок. После исправления владелец выполняет контролируемую повторную обработку. В DLQ запрещённого payload не должно быть: неподходящая схема блокируется до публикации, операционный карантин остаётся внутри домена.
6. Проверки схемы, полноты и контрольных сумм выполняются до публикации. В базовом варианте release ссылается на неизменяемые таблицы-кандидаты и их снимки; служебная запись содержит весь состав выпуска. После регистрации качества в OpenMetadata Airflow атомарно переключает указатель разрешённого release в PostgreSQL. Права этой роли ограничены реестром выпусков, без доступа к заданиям пользователей. Незавершённая публикация не видна порталу; повтор продолжает тот же release. Откат переключает указатель на сохранённый выпуск.
7. При использовании Nessie преобразование выполняется в отдельной ветке, после проверок — merge с проверкой конфликтов и фиксация commit в release. SQL всех частей отчёта использует зафиксированную версию. Nessie не создаёт общую транзакцию с PostgreSQL и OpenMetadata; доступ портала по-прежнему открывает последняя операция публикации указателя.
8. Каталог показывает владельца, версию, качество, время обновления и происхождение продукта. При отставании данных портал показывает время среза и статус; финансовое закрытие использует подтверждённую сверку, а не просто последнее доставленное событие. Удаление файлов/снимков учитывает активные отчёты, поддерживаемые releases и, при наличии Nessie, ссылки веток и тегов. Версионирование не заменяет резервного копирования файлов и каталогов.

Глобального порядка событий нет: порядок и версии отслеживаются по ключу агрегата. Изменение бизнес-правил не маскируется переиспользованием старого типа события. Отказ брокера не откатывает подтверждённую локальную операцию: outbox накапливается, а лимиты backlog и место в БД контролируются. Междоменные процессы используют компенсации и сверку вместо распределённой ACID-транзакции.

## Изменение существующих систем

| Текущее состояние | Переход | Состояние к месяцу 36 |
| --- | --- | --- |
| SQL Server 2008 DWH с бизнес-логикой | Инвентаризация процедур, владельцы данных, вынос операций по доменам; сверка с эталонными отчётами | Нет общей операционной логики; только архив по политике хранения либо полное отключение |
| PowerBuilder | Фасад и постепенная замена экранов оператора | Доменные приложения; старый клиент отключён после переноса операций |
| Кастомизированный Power BI | Совместимые витрины и параллельная сверка ключевых отчётов | Портал и доменные модели; Power BI может остаться ограниченным клиентом согласованных витрин, без зависимости от DWH |
| Apache Camel ESB | Антикоррупционный слой: перевод старых форматов в доменные контракты | Удалён с критического пути; временные мосты закрыты после прекращения потребителей |
| Python ИИ через DWH | Прямой разрешённый доступ к закрытым исследованиям и события жизненного цикла | Независимый ИИ-контур; аналитика видит лишь технические агрегаты |
| Go/Java финтех | Собственные БД, outbox, договорные события | Автономный банковский домен, доступный через контракты |

Для SQL Server 2008 резервный путь интеграции — инкрементальный экспорт со сверкой, если получение изменений из журнала недоступно. Новые доменные операции от этого способа экспорта не зависят.

## Этапы перехода

| Срок | Изменение | Условие перехода |
| --- | --- | --- |
| 0–2 месяца | Каталог критичных операций и данных, согласование доменов, контрактов и запретов | Владелец назначен каждому потоку, архитектура утверждена |
| 2–6 месяцев | Пилот расчётов и загрузки: Kafka, Object Storage, Iceberg, Dremio, Airflow и каталог | Два периода сверены; проверены повторы, публикация/откат release и восстановление; измерена задержка |
| До месяца 12 | Рабочий портал, конструктор, доступ и витрины пилотных доменов | Доменные пользователи строят отчёты; медицинские поля недоступны; UX принят |
| 6–18 месяцев | Расширение на банк и критичные домены, потоковые витрины, фасады Camel/DWH | Владельцы подтверждают качество и готовность дежурства |
| 18–36 месяцев | Подключение новых направлений и регионов, удаление синхронных legacy-связей | Нет активных потребителей старых интерфейсов; проверен архив и выполнены критерии отключения |

Во время миграции новый контур сначала читает данные для сверки. Для каждого агрегата сохраняется один владелец записи; переключение команд на новый сервис происходит после сверки результатов.

## Масштабирование

Обработчики масштабируются по партициям Kafka; рабочие процессы Airflow — по очередям доменов; вычисления Dremio — по ресурсам и очередям аналитических задач. Для BI и тяжёлых загрузок задаются раздельные квоты. Таблицы и бакеты разделены по владельцам, запросы ограничены опубликованными продуктами.

Свежесть lakehouse определяется накоплением пачки, расписанием, длительностью SQL и проверок. Переход к near-real-time требует измерения всей этой задержки. Если она превышает требование конкретного продукта, вводится потоковая витрина ClickHouse с отдельным контрактом свежести и сверкой с lakehouse. Ни наличие Kafka, ни Airflow сами по себе не гарантируют нужную скорость отчётов.

Новые направления подключаются через доменные адаптеры и версионируемые контракты. Для новых регионов предусмотрены автономные контуры; между ними передаются только разрешённые агрегаты. Kafka и базы размещаются с репликацией по поддерживаемым зонам Yandex Cloud. Меры против потери данных и сбоев описаны в [плане управления рисками](risk-management.md).

## Термины

DWH — корпоративное хранилище данных; ERP — система управления ресурсами предприятия; BI — бизнес-аналитика. DTO — структура данных входного запроса; OTLP — протокол передачи телеметрии OpenTelemetry; SQL — язык запросов к базе данных; TLS — защищённый транспорт.

CDC (Change Data Capture) — получение изменений из источника; KPI — бизнес-показатель; IdP — провайдер идентификации; OIDC — протокол входа; JWT — подписанный токен; JWKS — набор публичных ключей проверки токена; lineage — происхождение данных. SRE отвечает за надёжность эксплуатации, FinOps — за управление расходами на облако.

Release — опубликованный выпуск продукта; snapshot — снимок состояния таблицы; watermark — контрольная точка обработанных данных; backfill — пересчёт истории. Staging — закрытая промежуточная зона обработки, retention — политика сроков хранения.
